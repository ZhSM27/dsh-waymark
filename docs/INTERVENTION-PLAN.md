# Waymark 实时干预能力实施方案

日期：2026-11-02。状态：设计稿，尚未实现。本次仅核对项目与已安装 dsh 源码，不读取真实会话、不修改功能代码或用户配置。本文中的新命令、配置和内部类型均是 Waymark 设计提案，不是现有 dsh API。

## 1. 产品目标与交付范围

在 Agent 下一次行动前，把可核验的过程问题转成简短、可执行的反馈；证据充分时，可阻止特定重复调用，并允许用户一次性放行。最终通过任务完成情况和打扰成本评估收益。

建议分两次交付：

- **v0.2：实时观察与提醒。** 完成归档保护、增量状态、R1/R3 提醒、状态查询、频率限制和回放评估；R2/R4 先观察。
- **后续版本：有限拦截与人工暂停。** 仅对经过验证的 R1 情形开放；必须先完成取消、恢复、用户输入保留和界面验收。

不自动重试命令、改写工具参数、回滚文件、压缩上下文或修改 AGENTS.md。大输出保留原结果；自动截断或替换属于另一项设计。

## 2. 已核实的接入点

以隔离安装的 `0.2.1-rc.5` 为契约基线；本机 Desktop 的包版本为 `0.2.1-rc.2`，且包含定制改动。版本号相同也不能代替行为验证。

| 已安装接口 | 可用于什么 | 必须遵守的边界 |
|---|---|---|
| `tools/result(exec, result)` | 观察最终工具结果，更新增量状态 | 结果不可变；观察回调不承担等待用户的职责 |
| `session/event(session, event)` | 关联持久化 seq、轮次和输入边界 | 与工具事件去重；先验证会话可处理性再访问内容 |
| `agent/pre-step(payload, next)` | 下一次模型请求前传递短提示或接入等待 | 调用 `next()` 后保留其决定与全部消息；`reject` 不是可恢复暂停 |
| `tools/pre-execute(exec, next)` | 执行前策略；返回 allow/deny/cancel/ask | 参数已记录，不允许借此修改参数；尊重取消信号和下游策略 |
| `ctx.tools.guard(check)` | 同步拒绝某次调用；其他 guard 仍可拒绝 | 是附加拒绝条件，不能覆盖宿主权限；回调不能做异步 I/O |
| `tools/post-execute(exec, result, next)` | 附加插件来源的上下文 | `block` 是执行后改成错误结果，不能阻止已发生的副作用 |
| `ctx.workspaceRegistry.archivedSessionIds` | 获取宿主权威归档集合 | 宿主服务须已就绪；不得为获取集合自行引导全库扫描 |

`ToolExecution` 具备 `callId/rootCallId/token/parent/agent/signal`；运行时失败为 `result.error.info`，保存日志的失败信息在 `tool/result.data.error`。两个输入适配器应分别映射，不能假设结构相同。

两个实际影响设计的发现：

1. rc.5 已带 `dsh-repeat-tool-reminder`，按精确重复调用在 3/5/8 次附加提示，并在真人输入后重置。本机 rc.2 副本的这段监听被禁用。Waymark 的价值应来自失败原因、可观察状态变化、证据与干预反馈；需要测试与官方提醒同时启用时的表现。
2. 本机 `dsh-user-approval` 的实际 bundle 在 `decide()` 中直接返回 `allowed-once`。因此 `pre-execute: ask` 不能保证出现人工选择，也不能作为本机的暂停机制。Waymark 应使用自己的可信命令/交互入口；任何临时放行只解除 Waymark 的限制。

## 3. 三档能力及规则映射

额外提供 `off`。安装后默认 off，用户在当前会话显式开启；不自动改 profile 配置。

| 模式 | 行为 |
|---|---|
| observe | 只更新内存中的发现和拟干预记录，不向模型注入、不拦截 |
| warn | 在下一步前发出限量提醒，工具仍按宿主规则执行 |
| guarded | 在 warn 基础上，仅拦截满足严格条件的调用；人工暂停机制验收后才开放 |

| 规则 | 首期策略 | 后续升级条件 |
|---|---|---|
| R1 重复失败 | 两次已结束、同工具、同参数、同原因的失败后提醒 | 三次确证失败后，拦截下一次匹配调用；只开放已验证工具/错误类型。模糊相似、状态未知、中断、超时、后台任务均不升级 |
| R2 重复读取 | 先观察；充分证据后提供轻提醒 | 不自动拒绝读取：外部变化、上下文丢失和必要复核均可能使重读合理 |
| R3 巨型输出 | 输出完成后提醒下次缩小范围，建议 search/limit/片段读取 | 首次输出已发生，不能算作被节省；不自动篡改结果或拒绝大输出 |
| R4 用户纠偏 | 记录低置信度信号，重置旧提示或把控制权交给正常输入流程 | 不凭“停/undo”等关键词自动取消、撤销或回滚；优先尊重宿主明确的停止动作 |

以上实时阈值独立于离线复盘阈值；原 `failLoopMin=3` 不悄悄改变。两个模块应共用匹配和分类函数，不必共用动作阈值。

R1 拦截还须满足：前次调用已经结束、用户目标未变、没有相关成功修改或未知状态变化、没有并发未决操作、不是明确允许的轮询/重试流程。Agent 自称“无进展”不能作为证据；其生成的“继续”文本也不能授权放行。

## 4. 架构与事件顺序

```text
宿主事件 → 会话准入与归档检查 → 运行时适配 → 增量事实状态
                                                    ↓
                                              策略与提示预算
                                                    ↓
                              仅记录 / 下一步提醒 / 执行前拒绝
                                                    ↓
                                         人工反馈与效果评估
```

建议新增目录（尚未创建）：

```text
src/core/guard/             纯状态归约、策略、提示预算、决策类型
src/adapters/dsh-live.ts    运行时结果/会话事件映射和身份关联
src/host/guard-runtime.ts   生命周期、工具 guard、消息传递和取消
src/host/session-policy.ts  retro 与 guard 共用的归档准入
src/host/guard-controls.ts  可信人工控制、一次性放行、状态查询
test/guard-*.test.mjs       独立合成场景与宿主契约验收
```

核心接口拟采用 `reduce(state, event)` 更新事实、`decide(state, pendingCall, policy)` 输出动作。注入、磁盘、UI、时间和宿主 API 都在 core 外；时钟作为显式输入，方便确定性回放。

关键处理约定：

- 以会话及运行时 Agent 身份隔离状态，以 execution token/callId 关联结果；`tools/result` 更新一次，后来的日志事件补充 seq 证据，不再计数。
- 保存待执行、已结束、已被策略拒绝和取消的区别。Waymark 拒绝产生的错误单列，不能计入“命令又失败一次”，也不能重复增加浪费估算。
- R1 连续性沿用保守规则。不同工具、真人新输入、编辑、未知边界、上下文替换等会重置或降低置信度，暂不实现跨任意工具的语义推断。
- 提醒从最终结果形成待发队列，在下一次 `agent/pre-step` 注入带 Waymark 来源的短消息；下游若拒绝进入，则保留其决定并不擅自恢复。不得把插件提示伪装成真人输入。
- 同一步并发调用在前一结果出来之前已获准时，不事后宣称本可拦截。拦截不取消已启动的兄弟调用。
- 首期仅对当前显式开启、非继承的顶层会话启用干预。PTC 子调用、复合工具和 subagent 暂不拦截；需单独验证 parent/rootCallId、提交顺序和上下文可见性。
- 重启后默认关闭，不扫描历史恢复状态。会话清空、归档、Agent 销毁或插件卸载时清理状态与等待。状态上限触发时标记覆盖不足，不能基于残缺证据继续拦截。

## 5. 归档保护必须先完成

现有保护覆盖研究采样，生产 `/waymark retro` 尚未覆盖。这是实时能力实施的 G0 前置项。

- 对当前会话、显式 ID、`last`、回放、导出和实时事件使用同一准入规则；禁止以显式 ID 绕过归档限制。
- 首先只检查权威归档和所属关系元数据，获准后才访问内容；不对整库调用会加载归档记录的列表/索引路径。
- 在已运行宿主中读取已就绪的 registry；`last` 从已核验的未归档候选构造选择，不因接入新服务隐式初始化旧库。
- 归档状态不可确认时，不读取、不输出、不基于这份会话证据执行干预；提示该会话 Waymark 当前不可用，不替宿主取消工作。
- 每次事件处理和实际动作前复核准入。运行中归档后，丢弃缓存、撤销提示和临时放行、取消等待；恢复归档不自动恢复旧证据。
- 验收用合成归档记录和读取计数器证明正文零访问；包括启动、`last`、导出、归档变更与插件卸载。真实评估仍须先按元数据排除归档，旧材料也要重新核验范围。

## 6. 提醒内容与控制方式

合成示例：

> Waymark：同一检查已连续失败 2 次，错误相同。建议先定位错误原因，完成修正后再验证。证据：第 6–7 轮。

建议首期控制预算：同一规则和证据簇只提醒一次；每轮最多 1 次、每会话最多 5 次；每条不超过 400 个 Unicode 字符。均可配置，按规则合并提示，记录提示自身的估算 token。预算耗尽只抑制重复提醒，不能自动放行已被限制的调用。

消息仅包含必要证据引用和一条建议，不贴完整命令参数、长报错或原始用户片段。工具输出中的指令作为数据，不能修改模式、预算或放行令牌。

隐私说明须随功能更新：observe 的分析完全在本地；warn 若选择模型可见提醒，提示会随 dsh 原有的下一次模型请求发给其配置的模型服务。Waymark 不另建网络请求，但不能继续将此模式表述为“新增内容完全不出本机”。建议只注入规则、次数、轮次和通用建议，文件路径及正文证据留在本地；另提供仅向用户显示的提醒选项，该选项本身不能让模型自动改变行动。首期状态和反馈默认只在内存中，持久化评估材料通过显式本地导出完成；宿主仍会正常保存已注入的提示。

拟议命令：

```text
/waymark guard status
/waymark guard mode observe
/waymark guard mode warn
/waymark guard mode guarded
/waymark guard mode off
/waymark guard allow-once <decision-id>
/waymark guard feedback <decision-id> helpful|unnecessary|uncertain
```

`guarded` 在后续里程碑开放。模式仅作用于当前会话；需验证原生命令确属人工入口，模型工具不能借同一路由授予许可。

一次性放行绑定会话、决策、工具和完整参数指纹，建议两分钟过期；用户目标或相关状态变化后失效。仅允许下一次匹配的新调用，绝不自动重放旧调用，也不覆盖宿主安全策略。人工更改模式、放行、关闭的记录有明确来源。

公开 UI 最小信息：为何提醒/拦截、证据、下一步建议、当前模式，以及“仅本次允许/改换方案/关闭本会话干预”。按钮依赖宿主 UI 接口的下一轮契约验证；先交付可用的命令状态页，不能把计划中的按钮当作现有能力。

## 7. 拦截与暂停分开验收

**拒绝单次调用：** 优先使用同步 `tools.guard()`，只读取已准备的内存状态。返回理由表示本次工具体尚未执行；用 execution 身份记录 Waymark 决策归属。其 disposer 必须随插件卸载释放。放行通过不再返回 Waymark 拒绝理由实现，不返回强制 allow。

**暂停下一步：** `agent/pre-step` 的 `reject` 会结束本次提议，不能假装保留了已取出的用户输入。`agent.cancel()` 是取消，也不是挂起/恢复。不得通过这两个动作伪造无损暂停。

后续需验证可取消的 pre-step 等待与可信交互通道：原 messages 保留在待处理提议中；真人选择到达后重新检查会话、参数和宿主下游决定。停止、断线、超时、归档、卸载均必须结束等待，明确呈现取消/未执行结果，不能把超时当作同意。宿主若无法在等待期间接收控制命令，必须先补 UI 通道，不能留下死锁。

持续重复被拒绝时，不能靠无限返回错误来声称已打断循环。建议连续两次尝试已被 Waymark 拒绝后，进入上述人工暂停；该机制尚未验收前，产品只开放 warn，不发布自动 guarded。暂停针对下一步，既有工具副作用不回滚。

对未知宿主版本、接口失配或插件异常，显示降级状态并释放 Waymark 自己的 gate；继续遵守其他宿主权限。归档内容访问始终保持拒绝。不得用静默无限等待作为故障处理。

## 8. 分阶段实施与验收

| 阶段 | 工作 | 验收标准 |
|---|---|---|
| G0 基线修正 | 产品归档准入；核查 typed cancellation；澄清 R4 未知边界；rc.5 与本机定制版兼容矩阵 | 合成归档正文零读取；取消/策略拒绝不算实际失败；不支持的环境清楚降级 |
| G1 实时状态与回放 | core 归约器、live adapter、observe、状态上限和生命周期 | 在线处理与逐事件回放一致；乱序/重复/并发无重复计数；编辑、新输入、卸载正确清理 |
| G2 提醒 MVP | R1/R3 warn、消息来源、预算、命令控制、反馈和原生提醒兼容测试 | 提示对下一步可见且来源正确；不改原工具结果；预算测试通过；隔离 Web 实际界面可使用 |
| G3 有限拦截 | 严格 R1 条件、一次性放行、可取消暂停、UI/命令恢复 | 被拒绝的工具体调用次数为零；合法修复/轮询不拦截；停止/超时/断线/卸载不死锁、不自动执行；用户消息不丢失 |
| G4 效果验证 | 合成挑战集 + 获准未归档真实会话的 shadow 评议 + 新任务对照 | 分规则报告有用/无用/不确定和样本量；任务完成、验证、提示成本一起比较；未达到门槛的规则停留在 observe/warn |

每阶段小步本地提交，运行适用测试并报告；本计划不自动授权部署到用户当前 profile，也不构成公开发布许可。

核心测试至少包含：同一失败重复、修改后复测、不同参数和错误、并发同命令、中断、超时、延迟结果、拒绝回流、相同内容重读、读范围变化、外部状态未知、真人纠偏与插件注入的区别、上下文替换、PTC/子代理隔离、两个插件共存、旧 permit 重放和归档状态变化。

性能目标暂定：普通同步决策 p95 < 5 ms；同步 guard 不做文件/网络/模型调用。增量状态建议限制每会话 200 个调用摘要、20 个待发决策，完整正文不常驻。基准须记录硬件及输入规模，大输出使用有界处理，超过上限时保守降级；这些是验收目标，尚未实测。

## 9. 效果口径与上线门槛

- 旧会话回放只验证“在当时已知信息下会采取什么动作”，禁止窥视未来成功修改或后续输出。它无法证明模型收到提醒后会怎样行动，也不能直接算实际节省。
- 当前 R1/R2 缺少确证自然正例，不能因合成测试通过就默认开启拦截。对新获得且允许使用的会话独立判读，并检查未触发窗口。
- 建议 guarded 的最低试点门槛：至少 20 个经去重的 R1 候选决策、覆盖至少 5 个独立任务；可判定项中至少 90% 被认同值得干预，不确定项单列。该门槛仅用于是否进入小范围试点，不证明普遍准确率；不足时继续 warn。
- 代理评议与用户反馈分别记录，不能把代理同意冒充用户认同。只按自动生成提示的数量判断成功没有意义。
- 新任务评估同时记录：任务完成与最终验证、人工接管次数、提示/暂停次数、放行次数、后续重复、耗时和新增上下文体积。按任务类型匹配或在可重复的合成任务中做对照，避免把任务难度差异解释成干预收益。
- 不声称“省下被阻止调用的精确 token”；未来输出未知。可以报告阻止的调用数、历史同类输出估算和实际模型用量，但三者分开。

## 10. 实施前待实测的问题

以下问题不阻止完成设计稿；对应能力在合成宿主试验完成前不开放，不臆造 API：

1. pre-step 等待期间，原生命令和 UI 是否仍能可靠到达同一 live Agent？断线与卸载如何结算已 claimed 的输入？
2. 新插件 MessageSource 的类型扩展、日志保存、UI 呈现、导出与 R4 排除能否贯通？
3. 同步 `tools.guard()` 的拒绝如何与最终错误可靠关联，并保留“未执行/策略拒绝”的事实供重启后复盘使用？不以错误正文匹配代替身份关系。
4. 原生重复提醒启用状态如何可靠检测？未核实前不自动改其配置；不能保证同时启用时完全不重复提示。
5. PTC、复合工具、子代理及后台任务的提交边界是否可支持相同策略？首期明确不覆盖其拦截。
